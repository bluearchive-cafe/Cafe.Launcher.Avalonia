# ADR-032：游戏进程按「名字家族」识别，卸载等文件操作只在整族退出后放行

- 状态：✅ 已接受
- 日期：2026-09-15
- 来源：用户要求「卸载操作只有在游戏相关进程、反作弊退出时才可用」
- 相关：ADR-029（卸载预检失败不再静默）、ADR-030（卸载可彻底清除）

## 背景

卸载、安装、更新都要先问一句「游戏是不是在跑」，此前问的是**一个名字**：`GameConfig.Name`（`xldr_BlueArchiveOnline_JP_loader_x64`），加上本会话跟踪到的宿主进程句柄。

实机回归证明这个问法不够：卸载在游戏仍在运行时放行了，删除撞在被占用的目录上，最后留下一层删不掉的残留（见 ADR-030「已知限制」）。实测 Blue Archive 启动后的进程家族是三个：

| 进程 | 来源 | 旧检测 |
| --- | --- | --- |
| `xldr_BlueArchiveOnline_JP_loader_x64` | `game-launcher-config.json` 的 `name`，启动器启动并跟踪的宿主 | ✅ 认得出 |
| `xldr_BlueArchiveOnline_JP` | 宿主派生的同族子进程（反作弊宿主），**父进程被重挂到 `services.exe`** | ❌ 名字不同 |
| `BlueArchive` | `game-launcher-config.json` 的 `params` 里的游戏可执行文件 | ❌ 名字不同 |

更糟的是宿主的存活时间：实测宿主在游戏起来后就退出了，句柄随之失效，名字扫描又只认宿主——**三者全部漏掉**，「游戏在跑」被报成「没在跑」。这正是强杀或异常退出后反作弊仍占着目录的那一档。

同时，实测三个进程的可执行文件路径**全部读不到**（`Win32_Process.ExecutablePath` 为 null，反作弊保护进程对象），所以「按镜像路径是否落在游戏目录内」这条本来最直白的判据不可用。名字来自系统快照，保护不到。

## 决策

1. **已知名字从游戏自己带来的配置里取**（`Services/GameRuntime/GameProcessNames.FromLaunchConfiguration`）：宿主名（`name`）+ 启动参数里的可执行文件（`params`）。不硬编码游戏名，换游戏不用改代码。

2. **同族识别以 `_` 为界做前缀匹配**，两个方向不对称：
   - 进程名以 `_` 为界在已知名之后续写 → 认（已知名的变体）；
   - 已知名以 `_` 为界在进程名之后续写 → 认，**但要求进程名至少两段**：单段名字太泛，不该凭前缀把整族认领过去（`xldr` 不该匹配 `xldr_BlueArchiveOnline_JP_loader_x64`）。
   - `_` 作分界是为了让「同名家族」而不是「恰好同前缀」成立：`BlueArchive` 不会匹配上 `BlueArchiveData`。

   于是三个实测进程全部落在族内，而 `explorer`、`Cafe.Launcher.Avalonia`、`BlueArchiveData` 都不落。

3. **`IGameProcessTracker` 的返回值从布尔变成名字列表**（`FindRunningGameProcessesAsync`）。调用方要报给用户的是「实际在跑的那几个」，而不是配置里那个宿主——宿主已经退出、真正占着目录的是反作弊宿主时，报宿主就是假话。句柄仍在的宿主名由 `Register` 时记下的进程名兜底（读不到就回落已知名字的第一个）。

4. **探测走一次系统快照**（`Process.GetProcesses()` + `ProcessName`），而不是每个名字各扫一遍 `GetProcessesByName`：名字数量随配置增长，扫描次数不该跟着长。实测这条路径读得到被保护的三个进程名。

5. **两道闸门同一套判据**：卸载预检（`GameUninstallService.ValidateAsync`）与下载/安装/修复（`DownloadSession`）。卸载的拒绝文案点名实际在跑的进程（`游戏正在运行：xldr_BlueArchiveOnline_JP.exe / BlueArchive.exe`）；下载那条原本只有笼统一句「游戏正在运行，请关闭游戏后再修改文件。」，第 8 条落地后也点名进程。

6. **枚举失败按「没在跑」处理**：这是防误删的闸门，宁可让用户自己撞上别的检查，也不要因为一次快照读不到就把人永久挡在门外。

7. **卸载在删除前复查同一道闸门**（AUD-ARCH-008 跟进）：预检答的是「点卸载那一刻」的进程状态，而确认框可以一直开着（尺寸统计、用户离开），这期间从桌面快捷方式或 Steam 把游戏起来，预检的答复就已经过期——而卸载删的是一整棵安装目录。因此 `UninstallAsync` 在读到安装状态之后、删任何东西之前的同一位置跑一次复查，判据与拒绝文案由**同一个私有实现**（`FindRunningGameFailureAsync`）给出，所以预检与执行边界不会各说各话。这与路径守卫在同一提交里得到的处置同构（`EnsureCleanupTargetsAreDeletable` 预检一次、删除时经 `DirectoryTreeDeleter.Delete` → `EnsureDeletable` 再跑一次），失败经既有的 `ShowOperationResult` 落地（ADR-027）。

8. **下载/安装/修复同样是「判据 + 写入边界复查」，且判据不再要求本地配置存在**（AUD-ARCH-009 跟进）：
   - **名字来源加兜底**：此前判据只取本地 `game-launcher-config.json`，于是**全新安装**（还没有这个文件）时名字集合为空、闸门直接放行——游戏在跑也照样开始安装。现在没有本地配置时退回远端配置声明的**同样两个字段**（`GameConfigResponse.GameStartExeName` 与 `GameStartParams`）：本地配置落盘时写入的就是这两项（`DownloadSession` 的提交路径），两条路的判据因此一致。2026-09-15 复核轮修正：兜底起初只传启动程序名（`params` 传 `null`），漏掉的正是 `params` 里的游戏本体——反作弊宿主本来就被同族规则认领（它以宿主名为前提），所以原来的缺口描述指错了对象。
   - **写入边界复查**：计划阶段答的是「点下按钮那一刻」，而下载可能持续数分钟。下载阶段只写 `.tmp`，真正动安装目录（先删、后搬移）从 `InstallDownloadedFilesAsync` 开始，因此复查点落在它之前；命中即返回失败**而不是 Stop**——`.tmp` 留在盘上，用户关掉游戏后重试按已有字节继续（检查点按既有终局语义在这个出口丢弃，只有应用退出那一档保留供跨会话续传）。
   - **判法与报法各只有一处**：计划阶段与写入边界共用 `FindRunningGameFailureAsync`；「运行中的进程怎么写给用户看」（名字补回 `.exe`、` / ` 连接）收进 `GameProcessNames.DescribeForDisplay`，卸载那条也改走它——两个入口看到的名字因此一致（决策 5 里「卸载点名、下载保持原文案」的旧差异就此取消）。

## 被否决的替代方案

**按镜像路径归属游戏目录。** 最直白、最不依赖命名约定，实测不可用：反作弊保护进程对象，三个进程的 `ExecutablePath` 全部读不到。将来若某个运行环境（Wine/UMU）不保护进程，这条路可以重开。

**硬编码名字表**（`BlueArchive`、`xldr_*`、`XignCode*`）。过不了自己这关：名字是游戏与反作弊的实现细节，换版本就可能变，而且写死之后没有任何东西能证明它还对。从配置推导至少把宿主与游戏可执行文件交给游戏自己声明。

**把「同族」做成公共前缀匹配**（不带 `_` 分界）。会让 `BlueArchiveData` 这类同前缀的无关进程拦住卸载。

**在 UI 上禁用卸载入口。** 「不可用」的呈现方式本仓库已有定论（ADR-029）：拒绝要**就地说明原因**，而不是把入口藏起来。用户看到「游戏正在运行：…，请关闭游戏后再修改文件」比看到一个灰按钮知道得多；而且禁用态要引入实时进程轮询，等于把域内判定搬进视图层。

**追踪宿主进程的整棵子进程树。** 反作弊子进程的父进程被重挂到 `services.exe`，树已经断了——实测拿到的 `ParentProcessId` 是 1008（`services`）。

## 后果

- 卸载、安装、更新、修复的「游戏在跑」闸门覆盖整族进程，不再只看配置里那个宿主；宿主提前退出、只剩反作弊宿主时也不再放行。
- 卸载的拒绝文案从「宿主的名字」变成「实际在跑的那几个进程名」，可执行文件后缀由调用方补回（与启动器别处称呼可执行文件一致）。
- `IGameProcessTracker` 的契约从布尔改为名字列表；测试替身与既有用例随之更新。
- 守卫：`GameProcessNamesTests`（名字集合从配置推导、忽略非 exe 参数与重复项、族的正反例含 `xldr` 单段与 `BlueArchiveData` 同前缀反例；`DescribeForDisplay` 的 ` / ` 连接与 `.exe` 补回）、`GameProcessTrackerTests`（句柄优先、扫描回落、句柄活着但扫描看不见时用注册时记下的名字）、`GameUninstallServiceTests.UninstallAsync_WhenOnlyTheAntiCheatHostIsStillRunning_RefusesAndNamesIt`（夹具按实测启动配置构造——宿主名 + `params` 里的游戏可执行文件；替身按真实判据作答，只在请求的族里含配置宿主时才报反作弊宿主在跑，并断言每个探针都带齐两个名字。于是「判据来自 `name` + `params`」是这条用例成立的前提：漏掉 `params` 只认宿主时它红。2026-09-15 复核轮更正——此前它做不到：替身忽略入参、夹具用的合成名与判据无关，实测把 `FromLaunchConfiguration(name, null)` 注入后照样绿）、`GameUninstallServiceTests.UninstallAsync_WhenTheGameStartedAfterThePrecheck_RefusesAndDeletesNothing`（第 7 条的执行边界复查：探测分两次——预检时没在跑、删除时在跑；断言失败码、点名进程、且清单文件/安装状态/目录/快捷方式全未被动过。把复查拆掉时这条会红，已做变异验证）、`GameDownloadServiceTests.InstallOrUpdateAsync_WhenTheRemoteDeclaredExecutableIsRunning_RefusesBeforeWritingAnything`（第 8 条的远端兜底：替身只在请求的名字里含 `BlueArchive` 时报在跑，等价于证明名字确实来自远端配置；断言游戏文件、本地清单与检查点一个都没写）、`GameDownloadServiceTests.InstallOrUpdateAsync_OnAFreshInstall_DerivesTheGateFromTheRemoteHostAndItsStartParams`（第 8 条的兜底要按远端声明的两项算：夹具把宿主名与 `params` 里的游戏可执行文件写成两个不同的名字，替身只在请求里含后者时报在跑，并断言判据里两个名字都在——只传启动程序名时这条红）、`GameDownloadServiceTests.InstallOrUpdateAsync_WhenTheGameStartsDuringTheDownload_RefusesBeforeTouchingTheGameDirectory`（第 8 条的写入边界复查：第二次探测才报在跑，断言目标文件未落地而 `.tmp` 留在盘上）、`GameDownloadServiceTests.InstallOrUpdateAsync_WhenTheGameStartsBeforeTheZeroDiffCommit_RefusesAndWritesNothing`（同一道复查覆盖「差异为零但状态过期」的提交路径——它也往安装目录写两个状态文件；断言本地清单逐字未变、检查点未落盘）、`GameUninstallServiceTests.BuildCompletionMessage_*`（完成文案的四个状态）。上述用例均已做变异验证：把远端兜底改成空或只传名字、把复查判据喂空、删掉提交前的复查、回退文案组合，各自对应的用例变红。
- 顺带修掉一处测试脆弱：`GameDownloadServiceTests` 原先用真实进程扫描，开发机上开着游戏就会让提交路径的用例集体撞上闸门（实测发生过）。现在固定为「没有游戏在跑」，用例不再随环境变色。

## 已知限制

- 名字识别依赖「族名以 `_` 为界同前缀」这一约定。Blue Archive 实测成立；换一个宿主命名风格完全不同的游戏（例如宿主与游戏可执行文件毫无前缀关系且不在 `params` 里）会退化成只认配置里那两个名字，需要重新确认。
- `params` 的形态覆盖来自 `GameProcessNamesTests` 的形态用例（开关、路径限定、带引号、尾随空白、非 `.exe`），仓库**没有**随附实测的 `game-launcher-config.json` 样本：游戏换成另一种写法（可执行文件不在 `params` 里、用别的引用形态）时形态用例不会预警，只能靠实机复核。2026-09-15 复核轮即因此发现一例真缺口——判后缀用的是未归一的原始串，带引号或带尾随空白的路径会被静默丢掉，现已改为与提取同一个归一。
- 反作弊若把进程名改成与配置完全无关的样子，这里认不出来。目前没有比名字更可靠的用户态信号——镜像路径被保护，父进程关系被重挂。
- 进程枚举失败时按「没在跑」放行：`ProcessService` 吞掉 `InvalidOperationException`/`Win32Exception` 并返回空表。这是有意的取舍（不要因为一次快照读不到就把人永久挡在门外），但代价要写明白——游戏在跑时会进入删除，随后撞上被占用的文件：卸载走 `IOException` 失败路径，彻底清除把锁住的条目当残留报出，正是这道闸门想避免的那种残留。这条放行语义没有测试：`ProcessService` 自身零用例（替身都在 `GameProcessTracker` 那一层），枚举失败的行为因此没有被钉住。
- Unix 上这道闸门结构上弱得多：`Process.GetProcesses()` 的 `ProcessName` 在 Linux/macOS 取的是内核 `comm`（15 字符封顶），`xldr_BlueArchiveOnline_JP_loader_x64` 与 `xldr_BlueArchiveOnline_JP` 都截成同一串，等值与「以 `_` 为界续写」两条规则都不成立；`Path.GetFileName` 在 Unix 只认 `/`，Windows 风格的 `params` 也提不出名字。仓库发布 linux-x64/osx-arm64，Wine/UMU 安装因此实际上没有这道闸门——它不误报（空表即放行），但也不拦。
- 第 8 条的远端兜底按远端配置声明的**两项**推导（启动程序名 + 启动参数），与本地配置落盘时写入的两个字段同源，所以全新安装与已安装两条路的判据一致。2026-09-15 复核轮在此更正两处：此前兜底只传启动程序名（`params` 传 `null`），漏掉的是 `params` 里的游戏本体，而原文把漏掉的对象写成了反作弊宿主——宿主恰恰是兜底能认领的那一个（同族规则本就以宿主名为前提）。文案与代码在同一次复核里一并修正，`InstallOrUpdateAsync_OnAFreshInstall_…` 是这条的守卫。
