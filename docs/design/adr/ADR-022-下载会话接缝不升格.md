# ADR-022: DownloadSession 内部接缝维持私有分段，不升格为独立类

- 状态：**已接受**（2026-09-13，架构评审重审否决；其真实剩余价值以收缩形态落地于 15815d6）
- 背景：
  - 2026-09-13 架构评审候选 07 将「`DownloadSession` 内部接缝：规划与执行分离」列为 Worth exploring：该模块 708 行、只有 `RunAsync` 一个观察口，建议把私有分段升格为 `PlanAsync → DownloadPlanPreparation` / `ExecuteAsync(plan) → GameOperationResult` 内部接缝，让闸门类测试离开 HTTP/文件系统假体层。
  - 实现前重审发现，**提议的接缝已经以同名存在于代码中**：`PrepareDownloadPlanAsync` 返回的私有 record 就叫 `DownloadPlanPreparation`，执行半段是 `RunDownloadVerifyLoopAsync` 且已委托给独立的 `DownloadExecutor`，diff 计算已在独立的 `ManifestDiffCalculator`。升格为独立类只是移动可见性 + 搬代码，删除测试不过——什么都删不掉。
  - 评审代价清单四项，重审后两项已被候选 08 支付、两项为误判：
    - 「16 个 HttpMessageHandler/Stream 假体」：已被候选 08 的批级 `IDownloadTransport` 接缝消灭（`StubDownloadTransport`），测试文件中 handler 提及归零。
    - 「内部静态被 9 个测试直捅」：已迁入专门的 `DownloadSessionTests.cs`，主测试文件零引用——直捅面已隔离。
    - 「ACL 探测 hack（DenyCreateFiles）」：仅 1 处，且是「会话 × 真实写探测」的唯一集成点；`DirectoryWriteProbe` 本身已有专属直接测试。注入化需给 13 参数的 `DownloadSessionContext` 再加一席，换一个测试的写法，得不偿失。
    - 「CreateService 手接 13 个协作者」：它镜像的是 `GameDownloadService` 的真实构造签名，服务 ctor 不变它就不变。
  - 评审「纯函数化」前提不成立：计划段写 checkpoint、建目录、提交安装状态、发进度——每条失败路径清检查点是负载本身，不是可以抽离的杂质。
- 决策：
  - **不升格** Plan/Execute 私有分段为独立类。`DownloadSession` 保持单类封装「检查点保存 → 闸门 → 下载 → 校验重试 → 状态提交」全程；外部接口（`GameDownloadService` 会话生命周期）与内部私有分段签名均不变。
  - 收缩后的真实剩余价值（检查点终局清除不变量散布 14 处）**另行落地**：收敛为 `RunAsync` 出口单一 `finally`，按 `DownloadStopReason` 一次性判定（15815d6）。这是本候选重审中唯一通过删除测试的改动。
- 后果：
  - 代价：`DownloadSession` 仍是约 690 行的深模块，新增闸门仍落在同一个类里；闸门类测试继续经由全服务路径 + 替身协作者观察。
  - 收益：不引入只被测试消费的 `DownloadPlanner` 类；`DownloadSessionContext` 保持 13 席不再膨胀；检查点不变量从 14 处散布收敛为 1 处（见 15815d6，同时消除了「ApplicationExit 退出时在飞操作以非取消异常浮出 → 无条件 catch 误清检查点」的潜在分叉）。
  - 出站通道的两出口契约（2026-09-17，评审候选 R2-c14 的文档级收口）：文件下载通道经批级 `IDownloadTransportSource`/`IDownloadTransport`（候选 08 落地）走自己的长租约出口，`RemoteHttpTransport` 服务 API/更新/资源面板/图片缓存的 JSON/流取回；两者共用连接池与逐跳发送核心（`RemoteHttpRequestService.SendAsync`），但状态与缓冲纪律各归各——`RemoteHttpTransport` 类文档据此刻画边界，未重审本 ADR 不得提议合并两条出口。
  - 未来架构评审不得在未重审本 ADR 的情况下重提「升格 DownloadSession 内部接缝」。若未来计划段需要被第三个消费者复用（出现第二个适配器），或闸门测试在假体层继续增殖，本 ADR 必须重新裁决。
  - 评审方法教训（供后续评审引用）：接缝提议必须先确认「要建的东西是否已经存在」——私有方法 + 与提议同名的产物 record 意味着接缝已在，剩下的只是可见性问题；可见性本身不构成升格理由。
