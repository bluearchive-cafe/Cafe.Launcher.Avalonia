# ADR-043：程序集、命名空间与发行资产同名

- 状态：✅ 已接受
- 日期：2026-09-27
- 相关：`Cafe.Launcher.slnx`、`src/Cafe.Launcher/`、`src/Cafe.Launcher.UI/`、`src/Cafe.Launcher.Core/`、`src/Cafe.Launcher.Updater/`、`src/Cafe.Launcher.Updater.Core/`、`tests/`、`installer/`、`scripts/Build-Distribution.ps1`、`scripts/New-WindowsInstaller.ps1`、`.github/workflows/release.yml`、`tests/Cafe.Launcher.Tests/AssemblyNamingContractTests.cs`、[ADR-042](ADR-042-Avalonia启动器按Core与UI程序集分层.md)

## 背景

分层拆分（ADR-042）把表现层搬进独立程序集后，名字留下了三处不一致：

1. **宿主以 UI 工具包命名**。`Cafe.Launcher.Avalonia` 拆完之后只剩 12 个源文件（进程生命周期、
   单实例信号、组合根、崩溃进程拉起），但它同时是 exe 名、release 资产前缀、安装器的
   `EXECUTABLE_NAME`、macOS `CFBundleExecutable` 与 bundle id、Linux wrapper 的 exec 目标。
   产品名却是「Cafe Launcher」（安装器 `AppName`、快捷键、desktop entry、`/usr/bin/cafe-launcher`），
   于是用户看到的产品名与文件名/程序集名指向两个不同的东西，且那个不同的东西是**实现细节**。
2. **层级构词三套并存**。`Cafe.Launcher.Core`（产品.层）、`Cafe.Launcher.Avalonia.UI`（产品.应用.层）、
   `Cafe.Launcher.Updater` + `Cafe.Launcher.Updater.Core`（产品.Core）——新工程该沿用哪一套没有答案。
3. **命名空间不指示程序集**。`Cafe.Launcher.Avalonia.Constants`、`.Services`、`.Services.Diagnostics`
   同时被宿主与表现层两个程序集声明；表现层 170 个源文件里绝大多数声明 `Cafe.Launcher.Avalonia.*`。
   `using` 因此读不出依赖了哪个程序集，分层只能靠契约测试读，不能靠名字读。
   `Cafe.Launcher.Updater.Core` 更进一步：它的 `RootNamespace` 就是 `Cafe.Launcher.Updater`，
   与它的宿主工程共用一个命名空间。

代价是可量化的：程序集名被 XAML 的 `avares://…` 引用（10 处），命名空间被 `x:Class`/`xmlns` 引用
（约 90 个 `.axaml`）。因此这不是「顺手改名」，需要一次有窗口的收口。

## 决策

**每个工程的目录名、`.csproj` 名、`AssemblyName`、`RootNamespace` 与源码命名空间同名**：

| 工程 | 程序集 = 命名空间前缀 |
| --- | --- |
| `src/Cafe.Launcher`（WinExe 宿主） | `Cafe.Launcher` |
| `src/Cafe.Launcher.UI` | `Cafe.Launcher.UI` |
| `src/Cafe.Launcher.Core` | `Cafe.Launcher.Core` |
| `src/Cafe.Launcher.Updater` | `Cafe.Launcher.Updater` |
| `src/Cafe.Launcher.Updater.Core` | `Cafe.Launcher.Updater.Core` |
| `tests/Cafe.Launcher.Tests` / `tests/Cafe.Launcher.HeadlessTests` | `Cafe.Launcher.Tests` / `Cafe.Launcher.HeadlessTests` |

由这条同名规则引申出两条硬规则：

- **命名空间指明属主程序集**：同一个命名空间不得出现在两个程序集里。跨程序集可见性只经
  `internal` 与窄接口表达。表现层因此声明 `Cafe.Launcher.UI.*`，宿主声明 `Cafe.Launcher.*`，
  两者不再共享任何命名空间（ADR-042 的「只换程序集、不换命名空间」是搬迁期的过渡手段，
  到此结束）。
- **产品 token 只有一个**：发行资产前缀（`Cafe.Launcher_<tag>_…`）、安装器 `EXECUTABLE_NAME`、
  macOS `CFBundleExecutable`、Linux wrapper 的 exec 目标，与程序集名共用同一个
  `Cafe.Launcher`。**GitHub 仓库名（`Cafe.Launcher.Avalonia`）与 release 资产仓库
  （`Cafe.Launcher.Avalonia_Release`）是历史标识，刻意不改**：它们是对外 URL 与既成事实，
  改名会打断徽章、外链与文档。

被否决的替代方案：

- **保留宿主名 `Cafe.Launcher.Avalonia`，只改表现层。** 工具包名会留在 exe、资产名与 macOS
  bundle id 上——那正是用户能看见的部分，也是本次要消掉的东西。
- **保留命名空间、只改程序集。** 会得到一个叫 `Cafe.Launcher.UI` 的程序集里装着一堆
  `Cafe.Launcher.Avalonia.*` 类型：把「迁就历史」变成永久的第三条构词。
- **把 GitHub 仓库一起改名。** 影响徽章、外链、release 资产仓库与文档上的历史链接，
  收益只是「好看」，且不可回滚（重定向有成本）。
- **改 macOS bundle id 之外的身份标识（Inno `AppId`）。** `AppId` 是稳定 GUID，改它会让旧安装
  不再被识别为同一产品；本次只改 `CFBundleIdentifier`/`CFBundleExecutable`（zip 分发，
  无安装器升级链）。

## 后果

- 用户可见的一次性变化：Windows 可执行文件由 `Cafe.Launcher.Avalonia.exe` 变为
  `Cafe.Launcher.exe`；release 资产前缀由 `Cafe.Launcher.Avalonia_<tag>_…` 变为
  `Cafe.Launcher_<tag>_…`；macOS bundle id 由 `cafe.bluearchive.Cafe-Launcher-Avalonia`
  变为 `cafe.bluearchive.Cafe-Launcher`。产品名「Cafe Launcher」、安装目录、数据目录、
  单实例互斥名、安装标记（`.cafe-launcher-install`）与 Inno `AppId` 都不变。
- **自更新不受影响**：资产按后缀匹配（`_setup.exe` / `_win-x64.zip`）、信任锚是同 release 的
  `SHA256SUMS`；旧安装的资产选择逻辑不看前缀，因此仍能从改名后的 release 更新。
- XAML 的两类引用各归其位：程序集名出现在 `avares://Cafe.Launcher.UI/…`，命名空间出现在
  `x:Class`/`xmlns`。resx 的清单名随 `RootNamespace` 变为
  `Cafe.Launcher.UI.Resources.LauncherStrings`，两个生成器脚本与 Designer 同步。
- 新工程、新发行资产、新 XAML 资源 URI 都必须遵守同名规则；违反会红在
  `AssemblyNamingContractTests`（工程清单、同名词、命名空间前缀、资产前缀四条断言）与
  `AssemblySplitContractTests`（Core 命名空间前缀、IVT 名单）上。
- 历史文档（既有 ADR、`docs/research/`）保留当时的路径与名称，不再回改；当前状态以本文、
  ADR-042 的补充说明、`AGENTS.md` 与 `PROJECT_CONVENTIONS.md` §1.1 为准。
