# ADR-044：游戏身份与产品身份由档案声明并注入

- 状态：✅ 已接受
- 日期：2026-09-28
- 相关：`src/Cafe.Launcher.Core/Models/YostarGameProfile.cs`、`src/Cafe.Launcher.Core/Models/LauncherProductProfile.cs`、`src/Cafe.Launcher.Core/Constants/LauncherProfiles.cs`、`src/Cafe.Launcher.Core/Constants/LauncherPaths.cs`、`src/Cafe.Launcher.Core/Composition/LauncherCoreServiceCollectionExtensions.cs`、`src/Cafe.Launcher/Composition/ServiceConfiguration.cs`、`tests/Cafe.Launcher.Tests/AssemblySplitContractTests.cs`、[ADR-025](ADR-025-数据根由组合根解析并注入.md)、[ADR-042](ADR-042-Avalonia启动器按Core与UI程序集分层.md)、`docs/research/yostar-multi-game-onboarding.md`

## 背景

对接其他 Yostar 游戏的可行性研究（`docs/research/yostar-multi-game-onboarding.md`）先把事实钉住：
两份官方发行包（StellaSora CN 1.3.0 与 Blue Archive JP 1.7.2）是**同一套源码的两个构建**，
`@launcher/utils` 八个源文件里七个逐字节相同，主进程的全部游戏差异只是十来个配置槽
（游戏标识、API 基址、签名 salt、语言、托盘名、`AppUserModelId`、更新源、卸载清理命令、
日志端点、包内资源前缀）。也就是说，「支持另一个游戏」的成本主要落在**身份值放在哪里**，
而不是算法或界面。

而本仓库把这些值放在了最不容易换的地方：三个静态常量类。代价不是「多游戏才暴露」，而是
每次改一个 URL 都要先判断它属于谁：

- `Constants/ApiConfig.cs` 同时装官方 API（随游戏变化）与 Cafe 自己的发行仓库 slug、
  汉化镜像主机、资源面板 API（随产品变化）。
- `Constants/GamePaths.cs` 同时装游戏目录名与 `settings.json`、`unified.log` 这类
  跟游戏无关的启动器文件名。
- `Constants/LauncherConstants.cs` 里 `ProductName`（决定数据根）与官网链接混在一起，
  而 `Services/GameRuntime/GameRuntimeIds.cs` 又单独持有运行时身份。
- 消费方直接读静态常量，没有任何地方能回答「这个构建面向哪款游戏」。

## 决策

**把「哪款游戏」与「哪个产品」变成两个显式的值对象，值只声明一处，由组合根注入。**

1. **两个档案类型**（`Core/Models/`）：
   - `YostarGameProfile`：官方协议与安装布局里随游戏变化的全部值——`Tag`、`ApiBaseUrl`、
     `AuthorizationSalt`、`AuthorizationVersion`、`OfficialPackageHost`、`PackageAssetPrefix`、
     `RootFolderName`、`GameFolderName`、`GameExecutableFileName`、`GameStartScriptFileName`、
     `RuntimeId`、`OfficialWebsiteUrl`、`CookieLibraryRelativeSegments`。
   - `LauncherProductProfile`：随「谁在发行这个启动器」变化的全部值——`ProductName`（数据根名列）、
     发行仓库 slug、汉化镜像主机、自有服务地址与对外链接；GitHub API 地址与发行下载前缀由 slug 派生。
2. **唯一出处**：`Core/Constants/LauncherProfiles.cs` 声明 `LauncherProfiles.Cafe` 与
   `LauncherProfiles.BlueArchiveJapan`。任何地方都不得再写一份。
3. **注入而不兜底**：`AddLauncherCore(buildIdentity, launcherDataRoot, gameProfile, productProfile)`
   的四个参数都是必填。Core 不提供「按当前游戏取默认档案」的静态兜底——游戏标识写错不会在本地报错，
   只会让服务端拒绝，静默的默认值正是最难发现的那种错。pre-DI 路径（`Program.cs`、
   崩溃报告进程、`GameCompatibilityPaths`）没有容器，因此在那里显式写 `LauncherProfiles.Cafe`。
4. **`GamePaths` 收窄为 `LauncherPaths`**：只留启动器自有文件名与 Yostar 协议固定的两个状态文件名。
   游戏目录名、可执行名移入游戏档案。名字本身也要表明归属——一个叫 `GamePaths` 的类装着
   `settings.json` 是这次拆分要消掉的误导。
5. **`ApiConfig` 与 `GameRuntimeIds` 删除**：前者的成员按上表分入两个档案，后者只剩
   `RuntimeId` 一个值，随之进入游戏档案。
6. **判据一句话**：官方为另一款游戏重新构建时**会不会变**——会变则属于游戏档案；
   换个发行方会不会变——会变则属于产品档案。两者都成立的（汉化镜像主机名）当前放在产品档案，
   因为域名归产品方所有。

被否决的替代方案：

- **只重命名、不注入**（把 `ApiConfig.X` 换成 `LauncherProfiles.Cafe.X` 就收工）。值确实只剩一处了，
  但消费方仍从静态读，接缝没有被建起来，S1/S2 会把同一批调用点再改一遍；而这次改动的成本主要就是
  这批调用点。
- **给档案参数留默认值**（`YostarGameProfile? gameProfile = null` 退回 BA 档案）。省下约 150 处测试改动，
  代价是第二款游戏的宿主一旦漏传，就会拿 BA 的 tag 去写 `manifest.json` 与签名请求头——
  这正是本仓库在 ADR-025、ADR-028 里已经拒绝过的「静默兜底」形状。
- **现在就把档案做成可配置数据文件**（`profiles/*.json`）。当前只有一个游戏与一个产品，
  没有第二个消费者来证明文件格式的形状；等真正接入第二款游戏时再决定，
  档案类型已经把那一步的成本压到一个文件加载器。
- **现在就做运行期多游戏切换**。官方两份包的产品身份（包名、作者、`AppUserModelId`、托盘名、
  更新源、日志端点、卸载清理命令）全部按构建分叉，包内没有任何运行期游戏选择的数据结构；
  跟随官方，不做。

## 后果

- 换游戏 = 在 `LauncherProfiles` 加一个档案，由组合根登记；消费方不需要知道有第二个档案存在。
  改一个值也只需要判断一次归属，不用再问「这个常量该放哪」。
- 行为不变：协作者收到的值与拆分前逐字相同，固定向量测试（`vc`、认证签名、清单字段序）未改。
  `LauncherConstants` 只剩 `LogExportFolderName`、`DefaultThemeColor`、`ZIndexToast`、
  `LaunchGameArgument` 这类与游戏和产品都无关的常量。
- 值从静态变成构造参数后，测试必须在构造点声明游戏。共享的 `tests/Support` 不承载游戏知识，
  测试直接引用 `LauncherProfiles.BlueArchiveJapan` / `LauncherProfiles.Cafe`，
  因此「测试用哪款游戏」与生产组合根读的是同一份声明。
- `CorePublicImplementationsOutsideModels_AreTheDeclaredSet` 的声明表随之更新
  （去掉 `ApiConfig`、`GamePaths`、`GameRuntimeIds`，加入 `LauncherPaths`、`LauncherProfiles`）；
  档案类型本身放在 `Models/`，与「数据模型豁免域」的判据一致。
- 未收口的部分：`ResourcePanelUidService` 的资源面板 Cookie 域（`bluearchive.cafe`）与整个
  资源面板竖切仍是产品专属常量——它是产品功能而不是游戏身份，等资源面板需要支持第二款游戏时再谈。
  安装器 `AppId`/`AppName`、`PRIVACY.md`、发布说明、数据根名也仍按构建固定。
- 这一步不引入新程序集：跨仓库共享协议层（S1）与「构建期游戏档案」（S2）仍未决策，
  判据与成本记在 `docs/research/yostar-multi-game-onboarding.md` §6。
