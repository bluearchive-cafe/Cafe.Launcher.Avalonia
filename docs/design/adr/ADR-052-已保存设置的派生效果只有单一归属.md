# ADR-052：已保存设置的派生效果只有单一归属

- 状态：✅ 已接受
- 日期：2026-11-04
- 相关：ADR-024（已保存设置唯一写入方）、ADR-031（启动后行为可配置）、ADR-042（Core 与 UI 程序集分层）、ADR-051（活动生命周期共享实现按域持有）

## 背景

「已保存设置落盘之后要发生什么」原本散在三个调用点：设置页保存、首次启动向导完成、资源面板来源切换（`ShellLifecycle.SwitchSourceThenOpenPanelAsync`）。三处各自重复语言、主题、日志级别、资源面板、远程内容可见性与动效的应用，随后再各自刷新；顺序与覆盖面靠人工保持一致。

这带来三类可观察的问题：

- **入口漏项**：恢复默认设置只写盘并刷新，不应用日志级别等效果，也不在下载源变化时提示修复；同一份设置换个入口得到不同结果。
- **托付值不稳定**：壳的保存回调从 `SettingsEditor.Current` 回读，而那是用户仍可继续编辑的草稿；写入方返回的归一化值反而被丢弃。
- **两个接缝**：设置页同时持有「应用语言与主题」委托和「保存完成」事件，壳还要分别接线，接线顺序本身承担语义。

同时有两条行为必须保留：成功 toast 要在语言应用之后、慢刷新之前显示；远程内容可见性要在刷新完成前生效。

## 决策

1. 新增 `src/Cafe.Launcher.UI/Services/ISavedSettingsFollowThrough.cs`（窄接口，含 `SavedSettingsHandoff` 记录），设置功能只依赖这个共享接缝，不引用壳的具体类型。
2. `src/Cafe.Launcher.UI/Features/Shell/SavedSettingsFollowThrough.cs` 成为派生效果的唯一归属，按两段暴露：
   - `Apply(saved)`：立即应用语言、外观、日志级别、资源面板设置、远程内容可见性与动效，并捕获变更前的下载源，返回 `SavedSettingsHandoff`；
   - `CompleteAsync(handoff)`：下载进行中只把已保存设置写回内存快照；否则刷新，并在下载源变化且运行时状态为可启动或可更新时显示修复确认。
3. 触发方只保留自己的呈现：设置页显示成功 toast、向导隐藏自身、来源切换打开资源面板。保存命令等待 `CompleteAsync`，保证返回时壳状态已落定。
4. 所有入口传入写入方返回的已保存设置：设置页保存与游戏路径用 `SaveDraftAsync` 的返回值，向导完成与恢复默认用 `ReplaceAsync` 的返回值。`Apply` 之后发生的草稿编辑不得影响本次效果。
5. 恢复默认改走同一条路径，因此下载源变化且游戏已安装时会提示修复；首次向导完成时没有上一次快照，不提示。
6. 删除 `SettingsViewModel.ApplyLanguageAndTheme` 委托与 `SettingsSaved` 事件，壳改为设置一个 `SavedSettingsFollowThrough` 属性；生命周期仍负责在 `Wire`/`Unwire` 中挂接与拆除。

## 备选方案

- **保留多个事件、只抽公共函数**：调用方仍需各自按正确顺序调用每个效果，入口漏项与顺序漂移只是被推迟。否决。
- **把 toast、向导隐藏、打开面板也收进模块**：这些是触发方特有的呈现，收进来会让模块知道「谁触发了保存」，并迫使其承担与壳无关的 UI 流程。否决。
- **单段 `HandleAsync(saved, refresh)`**：无法同时满足「toast 在刷新前」「远程可见性在刷新完成前」与「下载中跳过刷新」三种时序。否决。
- **继续从 `Editor.Current` 回读**：草稿可被用户继续编辑，壳会应用一个从未落盘的值。否决。

## 后果

- 派生效果清单只在一处维护；新增效果或调整顺序改一个文件，所有入口一起生效。
- `SettingsViewModel` 不再需要保存完成事件，设置页的协调面缩小为一个属性。
- 下载源变化在恢复默认路径上也会提示修复，属于行为变化；用户可见说明需同步到文档工作区。
- 下载进行中仍只更新快照而不刷新，且不提示修复，保持既有契约。
- 壳仍拥有全部具体协作者，符合 ADR-042 的程序集边界；设置功能只看到 `ISavedSettingsFollowThrough`。
