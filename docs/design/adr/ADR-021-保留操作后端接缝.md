# ADR-021: 保留 IGameOperationExecutor 作为表现栈操作后端接缝

- 状态：**已接受**（2026-09-13，架构评审重审否决）
- 背景：
  - 2026-09-13 架构评审（`architecture-review-2026-09-13.html` 候选 03）将「删除 GameOperationExecutor 直通带」列为 Strong：该 63 行模块与同名接口的每个成员都是 1:1 转发（VM → journey → executor → 三个管线服务），生产代码侧通过删除测试——删掉后没有任何复杂度在生产代码重现。
  - 实现前的牵连面枚举推翻了这一结论。删除测试的正确问法是「删掉它，复杂度会在哪里重现」，而答案在测试侧：
    - `StubGameOperationExecutor`（171 行可脚本化替身）是 **15+ 个测试文件**的脚本化操作后端：GameOperationsViewModelTests、MainWindowViewModelTests 全部 partial（含 GameOperations/Motion/Settings/Lifecycle）、ShellLifecycleTests、WindowChromeViewModelTests、DebugViewModelTests 都靠它注入 `IsDownloadRunning`、预制操作结果与暂停状态。
    - Headless 工程的 `ThreadAwareGameOperationExecutor : IGameOperationExecutor` 专门模拟「`IsRunningChanged` 从工作线程触发」的竞态场景。换用真实 `GameDownloadService` 后，`IsRunning` 仅在活动下载会话存在时为真，表现层场景没有脚本化入口，该线程安全测试将直接丢失。
    - `GameOperationsViewModel` 本身不消费 executor（仅在构造 journey 时传递）；接口的真实消费者是 journey 与整个表现层测试栈。
- 决策：
  - **保留** `IGameOperationExecutor`、生产适配器 `GameOperationExecutor`（组合三个管线服务）与测试适配器 `StubGameOperationExecutor`。生产适配器 + 可脚本化测试适配器构成真实接缝——这是仓库标准的测试形态（与 `StubFatalCrashService`、`StubFileDownloadService` 同构），并非「假想接缝」。
  - 不删除、不合并，也不让 `GameOperationJourney` 绕过 executor 直接依赖 `GameLaunchService`/`GameDownloadService`/`GameUninstallService`。
- 后果：
  - 代价：新增一个操作需要在 4 处落笔（管线服务、executor 接口、executor 实现、journey 编排）；journey 对 executor 的 1:1 转发持续存在。这是接缝宽度换表现层可测试性的**有意支付**，不是待清理的遗留。
  - 未来架构评审不得在未重审本 ADR 的情况下重提「删除 GameOperationExecutor」。若表现层测试迁移到替代性的可脚本化机制（例如 journey 注入接口化、或下载后端出现可脚本化的真实入口），本 ADR 必须重新裁决。
  - 评审方法教训（供后续评审引用）：删除测试必须同时枚举生产与测试两侧的复现点；「一个生产适配器」不等于「假想接缝」——手写测试替身就是接缝的第二个适配器。
