# ADR-051：活动生命周期共享实现，按域持有

- 状态：✅ 已接受
- 日期：2026-11-04
- 相关：ADR-021（保留操作后端接缝）、ADR-026（停止意图由游戏操作域翻译）、ADR-031（启动退出不走关闭路径）、ADR-042（Core 与 UI 程序集分层）

## 背景

`ShellRefreshCoordinator` 与 `GameOperationJourney` 各自维护同一套「停机排空」状态机：一把锁、一个停机标志、一个在飞计数，以及计数归零时完成的 `TaskCompletionSource`。前者还额外负责刷新串行化门与 after-load 任务；后者在停机时要求后端按进程退出意图停止下载。

两处实现语义相同、机制各写一遍：修一个排空缺陷要改两处，测试也要在两个文件里各钉一遍。生命周期原语（`TaskSettler`、`LatestRefresh`）已有收拢到 `UI/Helpers` 的先例。

## 决策

1. 新增 `src/Cafe.Launcher.UI/Helpers/ActivityLifetime.cs`（`internal sealed`，`IDisposable`）：`TryBegin()` 发租约、`IsShuttingDown`、`LifetimeToken`、`BeginShutdown()`、`Cancel()`、`Dispose()`。排空状态机只此一份。
2. **共享实现，不共享状态**：刷新协调器与游戏操作旅程各自持有一个实例，不注册为 DI 单例。两个域的停机时间线互相独立，组合根不变。
3. `BeginShutdown()` 与 `Cancel()` 保持分离：前者封闭新工作并返回排空任务，后者只取消令牌（刷新协调器先 `BeginShutdown` 再 `CancelLifetime`）。两者幂等。
4. `Dispose()` 任意时刻安全：封闭新工作、取消令牌；令牌源的释放推迟到最后一个租约归还、且没有正在进行的取消之后。重复释放、释放后再取消都是 no-op。
5. 各域独有的部分留在原处：刷新串行化门与 after-load 握手留在 `ShellRefreshCoordinator`；`executor.Stop(DownloadStopReason.ApplicationExit)` 与停止意图翻译留在游戏操作域（ADR-026 不复述、不重开）。
6. `GameOperationJourney` 实现 `IDisposable`，由 `GameOperationsViewModel.Dispose` 调用。`ShellLifecycle` 的停机顺序与刷新协调器的延迟释放保持不变。

## 备选方案

- **一个共享单例**：会让刷新停机与游戏操作停机互相牵连——两者发生在不同时间线，测试也需要独立驱动。否决。
- **把差异参数化成回调**：把「停机时还要做什么」塞进原语的构造参数，等于换个地方重写两套实现，接口也没有变深。否决。
- **保留两套实现**：排空语义（计数、归零、幂等重复请求）一旦出错要修两遍，测试也要两遍，收益只有「少一个 internal 类型」。否决。

## 后果

- 排空语义只需在 `ActivityLifetimeTests` 验证；`ShellRefreshCoordinatorTests` 与 `GameOperationJourneyTests` 保留各自的集成用例（串行化、after-load 握手、停机拒绝新操作并等待收尾）。
- 原语不提及 `DownloadStopReason`，`GameOperationStopOwnershipTests` 的域边界守卫继续成立。
- 新增的是 `UI/Helpers` 下的 internal 类型，不扩大公共表面，不改变组合根与程序集边界。
- 租约的释放是幂等的：异步入口用 `using var lease` 收尾，异常路径与正常路径走同一条归还逻辑。
