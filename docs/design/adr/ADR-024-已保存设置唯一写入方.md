# ADR-024: 已保存设置只有一个写入方

- 状态：**已接受**（2026-09-14，架构评审候选 02 落地）
- 背景：
  - 2026-09-14 架构评审（`architecture-review-2026-09-14.html` 候选 02）指出「已保存设置发生变化」有多个写入方，而草稿与快照靠各调用方手工修补。复核把范围扩大：`settingsService.SaveAsync` 在生产里有 8 个调用点、归并后 6 个逻辑写入方——设置页保存、游戏路径选择、资源面板切换来源、恢复默认设置、关窗采集窗口几何、向导完成保存，另有资源面板 UID 与 UID 来源两个字段写入完全不碰编辑器。
  - 分叉是可复现的用户可见故障：手动 UID 由资源面板写入磁盘后，编辑器草稿里的该字段仍是旧值，用户在设置页改动任意一项并保存，整份草稿写回，UID 被静默回滚；设置页里没有该字段的编辑入口，用户无处发现。同一形状还出现在归一化上：落盘的是 `NormalizeSettings` 副本，而设置页保存后交回编辑器的是未归一化的草稿，于是「已保存设置」在编辑器里与磁盘上是两个不同的值。
  - 备选方案是把持久化并进 `ISettingsEditor`（让编辑器同时拥有草稿、快照与磁盘），它概念最少，但要让一个当前无依赖、可同步构造的状态持有者变成异步且带 I/O 的组件——它同时被 `RemoteHttpTransport` 在构造期闭包引用，并被二十余个设置测试直接 `new`。仓库另一处同类拥有者是「一个模块 + 窄接口 + 声明表」，故选后者。
- 决策：
  - 新增 `ISavedSettingsWriter` / `SavedSettingsWriter`（`Services/SavedSettingsWriter.cs`）作为已保存设置的唯一写入方，三个操作对应三种基底：`SaveDraftAsync()`（草稿成为已保存设置，设置页保存）、`UpdateAsync(change)`（在已保存设置上改字段，基底是设置快照）、`ReplaceAsync(settings)`（整份替换，向导完成与恢复默认）。
  - `LauncherSettingsService.SaveAsync` 返回真正落盘的归一化值；写入方以该值收口编辑器（`ApplySnapshot`），因此**落盘值、设置快照、设置草稿在每次写入后是同一个值**。
  - 六个写入方一律降为调用者，不再自己读盘、拼改、落盘、补草稿；`ShellViewModel.ApplyLanguage` 不再写设置草稿——展示刷新只改呈现，语言进入已保存设置只有「设置页保存」与「向导完成整份替换」两条路。
  - 结构不变量由 `SettingsWriteOwnershipTests` 守卫两层：`LauncherSettingsService.SaveAsync` 的生产调用方只有写入方；持有设置服务的生产文件是一张需登记的声明表。
- 后果：
  - 代价：设置写入多一层间接；测试里设置服务、编辑器、写入方必须成对装配（生产侧由 DI 单例保证），仓库为此提供 `SavedSettingsTestRig`。写入方以**设置快照**为字段改写基底而非重新读盘：这是「已保存设置是编辑器持有的那份值」的直接推论，也意味着应用运行期间外部对 `settings.json` 的手工改动不会在字段写入时被合并——与设置页保存一贯的整份覆盖语义一致。
  - `ISettingsEditor` 保持无 I/O、可同步构造，`RemoteHttpTransport` 的构造期闭包与既有设置测试不受影响。
  - 未来新增设置写入路径必须经 `ISavedSettingsWriter`；新持有设置服务的生产文件必须登记进 `SettingsWriteOwnershipTests`，登记时会看到这条规则。
